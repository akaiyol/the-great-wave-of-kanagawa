# Phase workflow — policy v2

## Startup and purpose

The two equally important goals are a source-recognizable procedural Great Wave ocean and an efficient, evaluated agentic system that can reach it. Canonical criteria are in `research/project-goals.json`, rendered in `GOALS.md`; neither goal can compensate for failure of the other. Read AGENTS.md, `research/agent-brief.md`, `research/agent-state.json` and the linked current phase. Load durable lessons by failure ID; retrieve historical evidence only when needed.

## Team

Lead owns scope, uncertain geometry, source integration, browser capture and decisions. Use one independent evaluator for plausible artifact reviews and the end-of-phase process review. Worker is optional for defined patches; researcher is optional for one exact blocker. At most one child active, one source writer, no recursive delegation. Existing role models stay unchanged. Use fresh minimal contexts and require policy v2 plus phase ID in the first handoff.

For a delegation: provide one failure ID, concrete hypothesis/construction, owned files, first artifact path, rejection condition and budget. The existing preflight must identify one source-backed anatomical relationship and the visible artifact coverage that will test it; necessary structural coverage is not artistic acceptance. Do not add a separate gate. Preserve others' edits. If the first artifact cannot be built, report the missing decision immediately. Narrow once; after another no-artifact result stop delegation and take serial ownership. Do not repeatedly poll unchanged work. Lead supplies captures unless explicitly assigned elsewhere.

## Phase lifecycle and 5% reserve

Use `node scripts/phase.mjs` to start a phase from a JSON specification, record its result, submit process review and regenerate the startup brief. See the CLI help. One executable hypothesis or bounded architecture change is a phase; do not redefine phase boundaries merely to avoid review.

At start set a planned token budget. Allocate 95% to implementation, artifact evaluation and checks; reserve the final 5% for process/log assessment. Stop new artifact work when the work allocation is reached; review the actual result, even if incomplete or rejected. Exact host/per-agent token usage is not exposed: estimates are estimates, actual values remain null unless telemetry supplies them. Tool counts, wall time and shared account usage are not exact compute. The tool enforces phase ordering/review completion, not an exact runtime token cap.

Before closing EVERY phase, without another user prompt, review: artifact delivery, repeated failure IDs, scope/evidence mismatch, wasted tests/calls, log consistency and changes worth retaining. Record at most three findings, retain/change/drop actions, evidence and the next concrete improvement. No geometry tuning inside the review reserve. Evaluator process mode provides independent critique at architecture changes, surprising failures and milestones; lead performs the same required review on cheap intermediate phases. Use only a compact phase record and matching lesson IDs initially; reserve source rereads for concrete discrepancies. Include expected context/setup cost in the review plan and record overruns. No-change is valid. If reserve is exhausted, record incomplete review and do not start another phase.

A phase cannot close or advance without its structured process review. Apply supported lessons to bounded `research/agent-memory.json`; archive superseded lessons through phase history. No automatic relaxation of acceptance criteria, reference pin, model/provider or permissions. Update workflow/role instructions only for evidence-backed process corrections; test fresh runtime adoption.

## Evidence and visual gates

Inspect the unchanged canonical scan before visual design. Work from convincing still to varied constructions, continuous scenery, then travel/release checks. Body and foam share the exposed boundary; local branch overlap or simple components do not prove an exterior union or open sky route. No fading joins. Compare native whole context before details and material texture. Passing numbers cannot override failing source anatomy or style. User artistic acceptance remains separate.

First capture one discriminating view. Run affected checks; reuse broad exact-regression evidence while owning source is unchanged. Bind source/reference hashes and viewport/DPR to captures; receipt excludes itself. Never regenerate reference pin or weaken fixtures for a pass. Record missing evidence explicitly. After two attempts preserve a failure signature, change representation/scale/interpretation; candidate renaming does not reset the count. Prior rejected method requires an explicit changed premise.

Historical action log is an index/archive, not a second changing account. Do not duplicate phase outcomes across prose logs and checkpoints.

The per-phase 5% reserve does not replace that account limit. Continue authorized work after each completed review. Stop for user request, allowance/external blocker or verified criteria; do not use recurring artistic-approval questions as the loop gate. ## Strategy extension v1 — 2026-11-04

Before a new phase hypothesis, obtain a fresh independent evaluator strategy review and record its evidence-pinned packet with `scripts/strategy.mjs`. When `agent-state.json` enables the strategy policy, the phase-start gate requires the matching review. See ADR-004 and the strategy CLI contract. Read the current linked strategy record with the brief; do not replay all strategy history.

Supply the objective, baseline, relevant failure IDs and evidence without telling the critic the lead's preferred answer. Require supporting and contrary evidence, explicit unknowns, a causal prediction, one discriminating test and a stopping budget. Keep a supported path when the evidence warrants it. Distinguish an implementation defect from a falsified premise, and a rejected candidate from an entire family of ideas. After two explicit failures in a family, re-entry requires an evidence-backed changed premise; renaming the family is not a pivot. Incomplete work is not automatically a failed premise.

Use continue/pivot/reject/defer. Do not silently override an independent rejection; seek reconsideration only with material new evidence and a bounded test. Review hypotheses rather than every parameter change. Calibrate the critic against outcome-hidden cases and later prospective results; never describe JSON compliance as critical-thinking accuracy. The existing artifact and final5%process gates remain.

Check the actual continuation goal at startup and milestones. For the current authorization, continue useful work to90%used in either account window, then checkpoint; do not end an intermediate run merely because a commit was pushed. Keep the effective user threshold in state. `run-health.mjs` diagnoses recorded inactivity only: it cannot run while the host sleeps, prove a pending agent is computing, or restart an interrupted runner. Do not create recurring jobs or change power settings without the corresponding user request. Researchers are read-only: the lead records their findings.

## Two-goal contract

Link every phase to ART and/or SYSTEM and state how it protects the other goal. The generated brief must retain both objectives and outstanding criteria. A promising still does not complete the agent-system goal, and sophisticated workflow does not complete the artwork goal. Final user artistic acceptance is separate from model review. Fixed sample counts and performance plans are provisional evaluation designs, not invented beauty thresholds. Compare quality and resource use against a declared baseline before claiming efficiency.

The lead owns the whole system and its public explanation. Update the architecture manifest and generated README diagram with every agent/workflow change, in the same commit. `project-contract.mjs check` must detect changed goal definitions, changed reviewed architecture inputs and stale generated documentation. The checker does not judge semantic fidelity; the lead and independent review still inspect that. Only an explicit user decision can authorize weakened goal requirements.
